0. 北极星目标（North Star）

本项目的核心目标不是“通用代码审计助手”，而是：

挖掘深层次的高危逻辑漏洞（RCE/任意文件读写/反序列化/SSRF/鉴权绕过/IDOR/状态机绕过等），
通过：扫描所有危险函数（sinks）→ 找到每个 sink 的所有调用链（入口点→…→触发 sink 的函数）→ 自动收集调用链涉及的代码上下文（函数定义+调用点+关键配置）→ 交给 LLM 做逐步推理与结论输出。

衡量完成度的唯一标准：

能不能在一个中大型仓库里，高召回地输出：

“哪些地方触发了危险函数调用（sink call sites）”

“每个触发点有哪些入口到达路径（call chains）”

“每条链的关键代码证据（带行号）+ LLM 的结构化审计结论”

1. 当前偏离点（请优先修正）

如果现有实现把重点放在：

“向量搜索去找危险调用（用 query: ‘调用 xxx 函数’）”

“LLM 只看一个函数片段 + 少量 related code”

“前端/项目管理功能堆得很满，但链路分析不硬”

那么这是偏离。原因：

危险函数命中需要的是确定性检索/静态匹配（AST/regex/token），不是语义向量检索；向量检索适合作为辅助（相似代码、补全上下文），但不该做主召回。

深层逻辑漏洞要靠 调用链上下文（入口→权限检查→业务状态→sink）才能判定。

2. 必须回归的“主流水线”（P0）
P0-1：危险函数触发点（Sink Call Sites）要“全量、确定性”找出来

不要用向量搜索当主手段。
实现一个 SinkCallScanner（或在现有 analyzer 内实现）：

输入：List[CodeUnit]
输出：List[SinkCallSite]，每个包含：

unit_id（发生在那个函数/handler里）

file_path, line_range

matched_rule_ids（命中的 sink 规则）

call_snippet（尽量精确到一两行）

sink_category（command_exec/file_read/file_write/deserialize…）

risk_level

匹配方式（按优先级）：

AST 精确匹配（Python 用 ast，JS/TS 如暂时没 tree-sitter，就先用稳健 regex + 语法上下文 heuristics）

退化为 code contains pattern（规则 patterns 允许 regex:/contains: 等）

关键：sink 的 patterns 应该是能匹配 代码调用表达式 的，而不是只能匹配 “函数名等于 xxx”。
例如 Python：os.system(、subprocess.run(、pickle.loads(
例如 JS：child_process.exec(、fs.readFile( 等

P0-2：调用图（Call Graph）只负责“内部函数之间”的可达性

构建 CallGraph（节点=CodeUnit，边=“A 调用 B”）

目标：用于求“从入口点到某个 sink 触发点所在函数”的路径

不要求 100% 精确的跨模块解析，但必须 高召回、可控误差

重要：调用链的终点不是外部库函数节点，而是“包含 sink 调用的那个 CodeUnit”。
（也就是：sink 是“事件/触发点”，不是调用图里的函数定义节点）

P0-3：枚举调用链（All Call Chains）要可控爆炸

对每个 SinkCallSite：

找所有入口点（handlers/controllers）到 unit_id 的路径

输出 CallChain：

entry_unit_id

path_unit_ids（入口到终点）

sink_call_site_id

depth

path_signature（用于去重）

必须做“爆炸控制”：

max_depth（如 12~20 可配）

max_chains_per_sink（如 30 可配）

去重策略：同一个 path_signature 只保留一次

优先保留 短路径 / 高危路径 / 入口点可外部访问的路径

P0-4：调用链上下文收集（LLM 必须读“链上的代码”）

实现 ChainContextBuilder：
对每条 CallChain 打包上下文（尽量紧凑，但必须足够）：

对链上每个 CodeUnit：

文件路径 + 行号范围

函数签名

函数代码（完整函数体，必要时裁剪到 token 上限）

对 sink call site：

命中规则摘要（risk、category、why）

精确 snippet（1~5 行）

附加“守卫信息”提取（轻量 heuristics）：

是否有 auth decorator / middleware（例如 login_required、@jwt_required）

是否有权限检查函数调用（如 check_permission/is_admin）

是否有路径校验/白名单（文件类）

是否有 shell=False / 参数化调用（命令类）

是否有 safe_load / safe deserialization（反序列化类）

这一步是“让 LLM 真正具备证据”的关键。
LLM 不能“自动读取文件”，工具必须把链上的代码喂给它。

P0-5：LLM 分析必须以“链”为单位输出结构化结果

LLM 不要只分析一个函数。必须分析“调用链导致的危险触发是否可被外部触发、是否可绕过、是否缺失校验”。

输出 JSON（强制 schema）最少包含：

chain_id

sink_category / risk_level

has_issue（true/false/uncertain）

issue_type（例如 command_injection/path_traversal/authz_bypass）

confidence

evidence（按链上节点列出：哪个文件哪几行、为什么关键）

exploitability_conditions（高层次条件，不要 payload）

fix_suggestion

notes（需要人工确认的点）

LLM 只负责逻辑推理与解释，不要让它承担“找哪些地方调用了 sink”这种工作。

3. 模块重构优先级（P0/P1）
P0（必须先完成）

把 “候选点发现” 改成：SinkCallScanner + CallGraph + ChainEnumerator

禁止把向量检索当主召回

让现有引擎改为：链驱动而不是“单点函数驱动”

规则系统增强：支持 “匹配代码调用表达式”，而不仅是匹配 function_name == pattern

P1（在 P0 跑通后再做）

向量库/RAG 的正确用途：

作为“链上下文补充”：查找同类校验函数、配置定义、相似漏洞变体（variant analysis）

不是用于“找 sink 调用点”

污点分析（taint）升级：

先实现“链上关键变量是否来自外部输入”的局部追踪

再逐步跨函数

前端纠偏：

UI 第一优先级是：按 sink 分类展示 → 每个 sink 触发点 → 展示所有调用链 → 链上节点可点击查看代码 + LLM 结论

非必要的项目管理/花哨报表暂缓

4. 明确的反目标（Anti-goals）

在 P0 完成之前，不要投入时间做：

复杂的多模型路由、复杂权限系统

很重的前端功能（工单、评论、仪表盘大而全）

“LLM 自己在仓库里搜索文件”的 agent 玩法（不稳定、成本高、不可控）

只靠 embedding 就下结论的“语义审计”

5. 交付验收（Definition of Done）

当满足以下条件，说明方向已经纠正：

给定一个仓库：

能输出所有危险函数触发点列表（包含文件与行号、规则命中）

对每个触发点输出至少 1 条入口到达链（能配置深度/数量）

每条链生成一个“上下文包”（链上函数代码+规则摘要+守卫提取）

LLM 按链输出结构化 JSON 结论（可在前端逐链查看）

把当前候选点发现逻辑替换为 SinkCallScanner（确定性扫描）

把 call graph 用于“入口→终点函数（包含 sink call）”路径枚举

把 LLM 的输入改成“调用链上下文包”，输出改成“链级 findings”

为高危类别（command/file/deserialize）写专用提示词模板（链级）
